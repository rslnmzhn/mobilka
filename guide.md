# mobilka — Архитектурный Гайд и Технический План

## 1. Обзор Проекта (Overview)
**mobilka** — это мобильный мульти-агентный AI-клиент на Flutter, вдохновленный современными интерфейсами агентных рабочих сред.

### Главные принципы
- **100% Remote Endpoints**: На мобильном устройстве **не запускаются** локальные модели. Всё выполнение моделей происходит через облачные API или внешние локальные роутеры (LM Studio / vLLM / Ollama).
- **Direct API & OpenAI-Compatible**: Прямая работа приложения с внешними эндпоинтами (OpenAI, Anthropic, OpenRouter, Groq, кастомный сервер с OpenAI-совместимым API).
- **RLM Markdown memory**: Единственная выбранная архитектура контекстной памяти. Это детерминированно выбранные, понятные человеку `.md` файлы, которые внедряются в запрос одним атомарным снимком и управляются пользователем вручную либо агентом после явного подтверждения пользователя. Альтернативный механизм контекстной памяти не планируется.
- **Мобильный адаптивный UI**: Фокус на потоковом чате с вынесением артефактов (кода, документов) и логов работы инструментов в нижние выдвижные панели (Bottom Sheets).

## 2. Архитектура RLM Markdown memory

В этом документе **RLM Markdown memory** означает детерминированный набор выбранных `.md` файлов, используемых как прозрачные источники истины:

1. **Выбор директории пользователя**:
   - При первом запуске пользователь указывает папку на устройстве (через File Picker / Storage Access Framework).
   - В этой папке создаются / читаются файлы:
     - `user_profile.md` — основные факты о пользователе, предпочтениях, стиле общения.
     - `project_context.md` — текущие проекты, задачи и контекст.
     - `system_instructions.md` — кастомные инструкции для агентов.
     - `memory_log.md` — хронологический лог обновлений памяти.

2. **Инжектор контекста (Context Injector)**:
   - Перед отправкой запроса к модельным эндпоинтам мобильный клиент завершает восстановление незавершённых изменений и атомарно считывает один согласованный снимок выбранных `.md` файлов.
   - Состав и порядок файлов детерминированы; весь снимок внедряется в системный промпт (System Prompt) как структура источника истины:
     ```text
     <user_memory>
     [user_profile.md]
     ...
     [project_context.md]
     ...
     </user_memory>
     ```

3. **Инструмент обновления памяти (Memory Tool)**:
   - Агентам предоставляется Tool (например, `update_memory_file`), позволяющий предложить обновление, дополнение или структурирование записей в `.md` файлах при появлении новой важной информации.
   - Предложенное агентом изменение применяется только после явного подтверждения пользователя.
   - Пользователь в любой момент имеет 100% контроль и может открыть эти `.md` файлы в любом текстовом редакторе или прямо в приложении.

## 3. Технологический Стек (Tech Stack)

### Frontend & Core (Flutter)
- **Фреймворк**: Flutter (Dart 3.x)
- **State Management**: `flutter_riverpod` + `riverpod_annotation`
- **Маршрутизация**: `go_router`

### Сеть и Стриминг
- **HTTP Client**: `dio` / `http`
- **SSE (Server-Sent Events)**: Поддержка потоковой передачи токенов (`fetch` / `eventsource` стримы) с поддержкой OpenAI-совместимого формата (`stream: true`).

### Хранение Данных и Безопасность
- **Чаты и сессии**: `Isar` / `Hive` (высокопроизводительные NoSQL БД для хранения историй переписки и списка артефактов).
- **API-ключи**: `flutter_secure_storage` (шифрованное хранилище Android Keystore / iOS Keychain).
- **Файловая память**: `file_picker` / `permission_handler` для работы с пользовательской папкой `.md`.

### UI & Рендеринг
- **Markdown & Code**: `gpt_markdown` / `flutter_markdown` + `flutter_highlight` (подсветка синтаксиса).
- **Панели и UI-компоненты**: `sliding_up_panel` или кастомные Flutter `showModalBottomSheet` для артефактов и логов.
- **Мультимодальность**: `image_picker` + `file_picker` (отправка фото и документов в Base64 или multipart).

## 4. Концепция Интерфейса (UI/UX)

```
+-----------------------------------+
| [≡] mobilka             [Model v] |  <-- Верхняя панель (меню, выбор модели)
+-----------------------------------+
| Agent: [Code Assistant / Search] |  <-- Бейдж текущего активного агента
|                                   |
| User: Создай скрипт парсинга...   |
|                                   |
| AI (Streaming):                   |
| Вот код скрипта. Я создал артефакт|
| [📄 Artifact: parser.py]          |  <-- Кликабельный бейдж артефакта
|                                   |
+-----------------------------------+
| [📎] [ Введите сообщение... ] [>| |  <-- Ввод сообщения + Attach Files
+-----------------------------------+
|  === Pull Up for Artifacts ===   |  <-- Bottom Sheet (Артефакты / Память / Логи)
+-----------------------------------+
```

### Основные Экраны и Модальные Панели
1. **Главный Чат**: Потоковый вывод текста, анимация генерации, отображение активности агентов и вызова инструментов (`Tool Calling`).
2. **Bottom Sheet "Артефакты"**: Выдвижная панель с вкладками для просмотра сгенерированного кода, Markdown-документов и файлов.
3. **Bottom Sheet "Память"**: Интерфейс просмотра и ручного редактирования `.md` файлов памяти с возможностью смены локальной папки.
4. **Экран Настроек**:
   - Управление API-ключами (OpenAI, Anthropic, OpenRouter, Groq).
   - Настройка кастомного OpenAI-compatible URL (для локального роутера на ПК/сервере).
   - Выбор дефолтных моделей и системных промптов.

## 6. Подводные Камни, Риски и Архитектурные Решения

### 6.1. Ограничения генерации `.docx` на мобильных устройствах
- **Проблема**: Библиотеки генерации `.docx` для Dart/Flutter (`docx_template` и др.) уступают по возможностям десктопным фреймворкам (`python-docx`). Сложная верстка, графики и кастомные стили трудноформируемы.
- **Архитектурное решение**: Для базовых документов (заголовки, списки, простые таблицы, форматированный текст) использовать шаблонизацию в Dart. При необходимости сложного форматирования использовать Markdown/HTML с последующим заполнением предзагруженного `.docx` шаблона.

### 6.2. Фоновый режим и засыпание приложения (Background Execution)
- **Проблема**: При сворачивании приложения во время длинного стриминга ответа или вызова инструментов ОС Android/iOS замораживает сетевое соединение через 10–30 секунд.
- **Архитектурное решение**:
  - Сохранять состояние чата и отправленного запроса в локальную БД (`Isar`/`Hive`) до вызова API.
  - На Android использовать `Foreground Service` с уведомлением в шторке («Идет генерация документа...»).
  - Реализовать логику авто-возобновления и обработки разрыва SSE-соединений при разворачивании приложения.

### 6.3. Нестабильность `Tool Calling` у сторонних и локальных моделей
- **Проблема**: Модели через OpenRouter/Ollama/vLLM могут возвращать невалидный JSON вызова функций или выводить вызовы инструментов обычным текстом в Markdown-блоках (` ```json ... ``` `).
- **Архитектурное решение**: Написать устойчивый парсер (Fallback Parser) на стороне Flutter. Если модель не использовала нативный API `tool_calls`, клиент должен отсканировать текст ответа, распарсить код/структуру и выполнить создание артефакта или файла памяти.

### 6.4. Безопасный доступ и шеринг файлов (Android FileProvider & iOS Security-Scoped URLs)
- **Проблема**: Прямой шеринг файлов с файловой системы на Android вызывает `FileUriExposedException`, а на iOS файлы из песочницы недоступны внешним приложениям без специального разрешения.
- **Архитектурное решение**:
  - Настроить `FileProvider` в `AndroidManifest.xml` для Android.
  - Использовать плагины `open_file_plus` и `share_plus`, которые корректно оборачивают пути в системные URI для открытия файлов в Microsoft Word, Google Документах и т.д.

### 6.5. Защита от переполнения оперативной памяти (OOM — Out of Memory)
- **Проблема**: Отправка нескольких тяжелых изображений (Vision API) в Base64 может вызвать переполнение OOM и краш приложения на устройствах с небольшим объемом ОЗУ.
- **Архитектурное решение**: Выполнять принудительное сжатие (Downscaling / JPEG compression) изображений на стороне Flutter перед кодированием в Base64 и отправкой в API.

### 6.6. Конфликты параллельной записи в файлы памяти (`.md`)
- **Проблема**: Если несколько агентов или процессов попытаются одновременно обновить `user_profile.md`, возможна потеря данных или блокировка файла.
- **Архитектурное решение**: Реализовать асинхронную очередь с блокировкой (Async Mutex / Lock) в `MemoryManager`, гарантирующую последовательную запись в `.md` файлы.
# Desktop memory file safety

Dart does not expose a portable no-follow regular-file open. Desktop memory
writes therefore use same-directory temporary files and atomic replacement
under a canonical-directory lock. The destination is revalidated with
`followLinks: false` immediately before rename, and links or non-files are
rejected. Adversarial replacement tests cover a link substituted at the final
replacement boundary. This protects app-mediated concurrent access; processes
outside the app do not participate in the in-process directory lock.
