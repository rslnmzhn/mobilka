## Verified controls

- No hardcoded secret values or committed signing files were found; CI references GitHub Secrets without printing their values.
- Android signing secrets are scoped to the preparation step, generated signing files are ignored, and an `if: always()` step removes the temporary keystore and password-bearing properties before artifact upload.
- The MSI is Authenticode-signed, signature verification must succeed before upload, and an `if: always()` step removes the temporary PFX from the runner temporary directory.
- Flutter, WiX, appimage-builder, and all third-party GitHub Actions are pinned to explicit versions or full commit SHAs; the release version is propagated to platform packaging.
- `release_assets/`, the generated root-level MSI name, and the build tree containing the generated MSI are ignored.

## Findings

### release_toolchain_partially_mutable — medium
file: .github/workflows/build.yml
line: 181
pattern: release packaging still installs unversioned operating-system packages and appimage-builder dependencies from live registries without artifact digest or lock-file verification
risk: upstream repository changes or dependency substitution could alter Linux release output without a corresponding repository change.
fix: use a reviewed immutable runner/container image and hash-locked packaging dependencies or verify downloaded artifacts against committed digests.

---

### tag_published_before_release — medium
file: .github/workflows/build.yml
line: 338
pattern: the stable tag is created in a separate job before the GitHub Release and its assets are published
risk: a publication failure can leave an authoritative tag without release assets, creating an operationally incomplete release but not directly exposing secrets or bypassing MSI signing.
fix: make tag and release publication one idempotent operation, or make retries complete the existing tag rather than resolving a new version.
